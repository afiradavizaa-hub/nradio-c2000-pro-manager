## 2. 通信协议（已实测跑通）

### 2.1 认证：HTTP Digest（MD5 + qop=auth）

前端 `getAuthType()` / `doLogin()` / `getAuthHeader()` 的算法：

1. 未认证访问任意受保护资源 → `401` + `WWW-Authenticate: Digest realm="Highwmg", nonce="...", qop="auth"`
2. 登录（`GET`）：
   - `HA1 = MD5(username:realm:password)`
   - `HA2 = MD5("GET:/cgi/protected.cgi")` ← 注意是 `protected.cgi`，不是 xml_action
   - `response = MD5(HA1:nonce:00000001:cnonce:qop:HA2)`
   - `GET /login.cgi?Action=Digest&username=..&realm=..&nonce=..&response=..&qop=..&cnonce=..&temp=marvell`
3. 业务请求（每个请求单独计算，`nc` 递增）：
   - `HA2 = MD5(METHOD:/cgi/xml_action.cgi)`
   - `response = MD5(HA1:nonce:nc:cnonce:qop:HA2)`
   - 请求头 `Authorization: Digest username="..", realm="..", nonce="..", uri="/cgi/xml_action.cgi", response="..", qop=auth, nc=00000001, cnonce=".."`

**一个反直觉但必须遵守的细节**：`uri` 与 `HA2` 里固定写 `/cgi/xml_action.cgi`，而真实请求路径是 `/xml_action.cgi`（lighttpd 做了映射）。实测照抄前端行为可 100% 通过，改动任一字符串都会 401。

### 2.2 数据接口

| 操作 | 请求 |
|---|---|
| 读 | `GET  /xml_action.cgi?method=get&module=duster&file=json_<接口名><13位毫秒时间戳>` |
| 写 | `POST /xml_action.cgi?method=post&module=duster&file=json_<接口名><13位毫秒时间戳>`，`Content-Type: application/json`，Body 为 JSON |
| 上传/备份 | `/xml_action.cgi?Action=Upload&file=upgrade\|backfile\|config_backup` |

时间戳后缀是原厂用来绕缓存的手段，不带也能通，但保留更贴近原厂行为。

**实测边界结论**：`*_set` 系列用 GET 访问会返回 `{"result":"1","msg":"api not found"}`，说明读写严格分离——`_info` 只读、`_set` 只写。

### 2.3 会话与异常

- 未登录 / 被顶下线时返回体含 `UNAUTHORIZED` 或 `KICKOFF`，前端据此跳回登录页；第三方软件应把这两种情况映射为"会话失效"并自动重登。
- `login_info.login_status = 1` 表示在线（第 3 方软件用它做心跳，原厂 10 秒轮询一次）。
- 原厂心跳：`setInterval(callJSON("login_info"), 10000)`。

## 4. 数据编码约定（踩坑点）

1. **文本字段存在两种 HEX 编码，已分别核对（初版判断有误，此处为修正后的结论）**
   - **SSID**：UTF-16 大端，每字符 4 位十六进制，规则等同于原厂前端 `UniEncode/UniDecode`。
     `004D006900460069002D0031003300320042` → `MiFi-132B`。写入时**必须**用同一规则编码，否则设备端显示乱码。
   - **终端名**（`client_list[].n`、`known_devices_list[].name`）：单字节 ASCII 的十六进制，可能带空格分隔。
     `" 44 45 53 4b 54 4f 50 2d 55 33 34 34 34 54 50"` → `DESKTOP-U3444TP`；
     `4f6e65506c75732d3135` → `OnePlus-15`。
   - 注意：原厂前端对终端名也调用了 `UniDecode`（按 4 位分组），在上述空格分隔格式下会解出乱码——属固件与网页脚本不一致的历史问题。
     本软件按字段语义分别解码，并保证任何异常情况下都退回显示原始值，不输出乱码、不丢信息。
2. **两套信号数值并存**
   - `status_info.rssi = -88`（已是 dBm，直接用）
   - `engineering_info.lte.rsrp/rsrq/rssi/sinr` 是基带原始编码值（当前 rsrp=55, rsrq=21, sinr=7, rssi=55），原厂前端**直接原样显示、未做换算**。第三方软件要显示 dBm 必须自行标定（方法：与 `status_info.rssi` 同步采样做线性对齐）。
3. **`sys_mode` 枚举**：`17` = LTE（当前），`5`/`15` = UMTS，`3` = 其它制式（前端分支）。
4. **密码字段**：`account_management_info.router_user_list[].password` 返回空串，密码不可读（正常）。
5. **流量口径**：`status_info.tx_byte_all/rx_byte_all` 是设备累计值；`device_management_info.client_list` 里 `rx/tx` 为累计、`rxm/txm` 为月度、`rx3/tx3` 为近 3 日——与页面 `mDataTraffic` 的字段一一对应。
6. **终端流量计数器会失真（2026-10-17 复测）**：字段单位确实是字节——原厂 `js/base.js` 的
   `FormatDataTrafficMinUnitKB(dataByte)` 按 `1024³` 换算 GB，且 `mDataTraffic.html` 本身只展示
   名称 / MAC / IP / 连接时长，不展示这些数值。真机上却出现单终端累计 `rx=36,371,032,162,688`
   （≈33.86 TB）、`tx=7,147,604,096,932`（≈6.51 TB），而同一时刻 `status_info` 整机自开机 22.5 小时
   仅 16.8 GB；该终端 4 小时前的计数还是 142 GB。结论：**失真来自固件计数器，不是单位换算**。
   本软件对「超过整机累计 2 倍」或「超过开机时长 1 Gbps 理论上限」的终端计数器标记为「计数器异常」
   并隐藏，本地历史同时丢弃此类跳变，只保留可信增量。
7. **电池字段只有四个（2026-10-17 复测）**：`battery_percent`（0–100）、`battery_charge`
   （0 未充电 / 1 充电中 / 2、3 已充满）、`battery_charging`（1 充电中）和 `battery_connect`
   （原厂页面未使用，语义未确认）。原厂 `dashboard.html` 只展示电量和充电状态；
   接口清单与脚本均无电压、电流、温度、剩余时间或累计耗电字段。详见 `docs/06-电池监测说明.md`。

## 7. 真机验证结果（软件侧自检）

写完通信层后，用与桌面软件**完全相同**的代码对真机执行了两轮自检：

| 项目 | 结果 |
|---|---|
| Digest 登录 + 18 个读接口字段解析 | 21 项全部通过 |
| `wan_set` 原值回写（写入设备当前值）+ 回读校验 | 通过，回读与写入前一致（NW_mode=2、MTU=1250） |
| `wlan_set` 原值回写 + 回读校验 | 通过（net_mode=4、channel=0） |

### 设备侧安全发现

三组原始 HTTP 对照实验（不经过本软件的任何逻辑）：

| 实验 | 结果 |
|---|---|
| 不带 `Authorization` 头请求 `/xml_action.cgi` 读取状态 | 成功返回完整数据 |
